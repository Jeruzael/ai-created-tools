# v1.29 Hardening Guide

Version: 1.29.0. Updated: 2026-10-31.

## What Changes for Users

The app still reviews local information only. It does not delete, move,
quarantine, install, repair, change the registry or alter Windows security.
Read-only diagnostics may be incomplete without suitable Windows permissions.

Refresh the dashboard after an upgrade or server restart. A missing/expired
session-token error is a reason to refresh, not to weaken browser protections.
Keep reports, allowlists, baselines and recovery copies private. Findings and
confidence levels remain review evidence, not safe-to-delete verdicts.

## Local API Contract

Bind only to `127.0.0.1` or `localhost`. Each request's Host must be an explicit
loopback alias with the **actual listening port**. Foreign hosts, duplicate Host
headers and absolute-form request targets are rejected. If Origin is present,
it must match the request's local HTTP origin, including the port. Foreign,
`null`, duplicate or mismatched origins are rejected. Cross-site and same-site
Fetch Metadata are rejected; same-origin and direct navigation are permitted.
Non-browser clients may omit Origin, but must still supply a valid token.

1. GET `/api/session` with the correct Host and same-origin context to obtain the
   current application's `csrf_token`.
2. Send it as `X-CSRF-Token` on **every other `/api/` request**, including GETs.
3. For POSTs, send one `Content-Type: application/json` and one valid
   `Content-Length`. The body must be a UTF-8 JSON object, at most **4 MiB**.
   Arrays, null, duplicate keys, non-finite numbers, malformed/truncated JSON,
   duplicate lengths and Transfer-Encoding are rejected before dispatch.
   Safety/review acknowledgement fields must be literal JSON `true`, not a
   string or the number 1.

### Boolean Options

Optional Boolean fields accept only literal JSON `true` or `false`. Only an
omitted field uses its default. Explicit `null`, strings (including `"false"`
and `"true"`), numbers (including 0 and 1), objects and arrays return HTTP 400
before job admission. Clients must not send stringified checkbox values.

| Route | Field | Omitted Default | Explicit Boolean Behavior |
| --- | --- | --- | --- |
| POST `/api/scans` | `includeReparse` | `false` | `true` opts into reparse traversal; `false` keeps it off. |
| POST `/api/security-checks` | `registryBackup` | `false` | `false` is accepted; `true` still returns 400 because backups are unavailable. |
| POST `/api/security-checks` | `wmiCheck` | Standard: `false`; Advanced: `true` | Selects WMI only when Advanced mode is selected. |
| POST `/api/security-checks` | `eventLogCorrelation` | Standard: `false`; Advanced: `true` | Selects Event Log collection only in Advanced mode. |
| POST `/api/security-checks` | `sysmonCorrelation` | Standard: `false`; Advanced: `true` | Selects optional Sysmon collection only in Advanced mode. |

Actual Boolean flags do not change the requested mode: Standard mode never
runs Advanced collectors, even if these flags are explicitly `true`. Existing
saved records are not rewritten. Scripts that previously supplied false-like
strings, numbers or null must send real JSON Booleans or omit the field.

The browser wrapper bootstraps once for concurrent calls, forces same-origin
transport, refuses remote API URLs and does not follow redirects. Bootstrap
failure can be retried. The random token is not embedded in HTML, records,
metadata or exports and is not persisted. API/HTML responses are `no-store`;
responses prevent MIME sniffing and framing. No permissive CORS is enabled.
An absolute 10-second header/body admission deadline and 16-request thread cap
limit stalled clients. The deadline is disarmed before admitted application
work, so it cannot interrupt an atomic persistence update. An expired socket
can close without a JSON response if its framing never completed.
Pre-admission busy/shutdown responses send a FIN and drain at most 64 KiB for
250 ms before closing, avoiding Windows TCP resets caused by unread request
headers without allowing an unbounded rejection drain.

| Status | Meaning |
| --- | --- |
| 400 | Invalid JSON, framing, identifier or action input. |
| 403 | Disallowed Host/Origin/Fetch Metadata, or missing/invalid token. |
| 404 | Unknown resource or missing saved record. |
| 405 | Unsupported same-origin OPTIONS; no CORS permission is granted. |
| 408 | Request body did not arrive within the read timeout. |
| 409 | Busy/shutting-down application, stale evidence or local recovery condition. |
| 411 | Content-Length is missing on a JSON POST. |
| 413 | JSON request exceeds 4 MiB. |
| 415 | Missing or unsupported JSON media type. |
| 500 | Unexpected local failure; no exception traceback is returned. |
| 503 | All 16 HTTP request-worker slots are occupied; retry later. |

Existing action routes and JSON response purposes remain. Scripts written before
v1.29 must add the bootstrap/token and JSON framing. Record/check/baseline IDs
must be the generated 32-hex-character IDs; paths are never accepted as IDs.

GET Installer review and process review are retained for compatibility. They
read local Windows data and can be expensive; they now require a token too.
Installer review updates an in-memory snapshot but does not modify the cache.
Protected manifest export remains an acknowledged POST, not a download URL that
an unrelated page can trigger without the session token.

## Operation and Cancellation Rules

Disk scans, Security Checks, Installer reviews and manifest exports share one
operation owner. Final admission and active registration are atomic. Conflicting
requests return 409; shutdown closes admission permanently for that session.
Installer work releases ownership on success and failure. Older workers cannot
publish over a replacement operation or clear its ownership.

Cancellation is cooperative. It signals the admitted worker and leaves the app
busy until that worker reaches a terminal state; Windows calls already in
progress are not forcibly killed. Cancellation accepted before finalization is
saved as cancelled. Once record finalization begins, cancellation is rejected
rather than reporting a cancellation that cannot be represented in the record.
Thread-launch and record-preparation/write failures become terminal failures,
not permanently running jobs. Exit remains blocked while owned work is active.
The server caps concurrent request threads at 16 and bounds request reads.
Shutdown rejects with 409 while another HTTP handler is in flight, including
process reads, incomplete headers and short persistence requests. Accepted
shutdown closes HTTP admission atomically and drains its own handler; rejected
application shutdown rolls that admission change back so cancellation still
works. It does not terminate a writer halfway through an update. Native calls
and an external Ctrl+C remain cooperative rather than forcibly interrupted.

## Local Persistence and Recovery

JSON is validated/serialized before publication, written to a unique temporary
file in the destination directory, flushed, fsynced, closed and published using
`os.replace`. Normal failures remove the temporary file and preserve the prior
destination. This is not a guarantee of durability across every filesystem,
power failure or forced process termination. A forced kill can leave a private
temporary file; it is not an authoritative record.

Allowlist add, removal and import lock the complete read-modify-validate-write
transaction. A stable sibling `.allowlist.local.json.lock` coordinates threads
and cooperating processes sharing the directory. Do not delete the lock file
while a dashboard process is running. Contention times out with a retryable
error, rather than silently dropping another writer's changes.
The default five-second contention deadline covers both the thread lock and
the cross-process lock; acquiring one does not reset the budget for the other.

The entire merged allowlist is validated, including the 5,000-entry limit,
supported schema and genuine Boolean `active` values. Missing files initialize
normally. Existing damaged, unsupported or unreadable files are not treated as
an empty allowlist and are not automatically replaced. There is no destructive
"reset everything" fallback.

Recovery procedure:

1. Stop all dashboard processes using this folder. Preserve the affected file
   unchanged in a private backup, for example `allowlist.local.json.backup-...`.
2. Restore a known valid private copy, or deliberately repair the JSON/schema.
   Keep the damaged original until recovery is verified. Never paste private
   findings or allowlist data into public issue trackers.
3. Restart and confirm the expected entries and coverage before making changes.
   If you lack a backup, inspect the damaged file manually; do not automatically
   discard its contents. Permission failures require correcting access to the
   app's private storage, not changing Windows security settings.

Related scan/security records, baselines and version metadata use the atomic
writer. Security finalization publishes one coherent record. Baselines/records
are validated when loaded; historical data is not migrated by overwriting it.
Keep the application and local storage in a private, writable per-user folder.
No cross-process job scheduler or protection from malicious same-user programs
is claimed; the allowlist file lock protects cooperating writers only.

## Collector Coverage

Coverage is stored separately from findings as `security-coverage-v1`, containing
eight standard collectors, file verification and five advanced collectors.
Every collector records selection, scope, source outcomes, counts and reasons.

| State | Meaning |
| --- | --- |
| complete | Selected collection succeeded within its stated scope; zero matches can be legitimate. |
| disabled | Optional collection was intentionally not selected. |
| unavailable | A required source/dependency was not available. |
| access_denied | Windows blocked collection. |
| partial | Some evidence was collected, but sources/verification were incomplete. |
| failed | Collection failed without successful complete coverage. |
| cancelled | Collection was interrupted or prevented by cancellation. |
| pending / running | Temporary lifecycle states, not completed inspection. |

Coverage is not a malware verdict. A finished run can have incomplete coverage.
Signature failures, candidate caps and source errors cannot become a clean
inspection. Completed evidence is retained when a later collector is cancelled.
The API, saved record, dashboard metrics and HTML/JSON reports use the same
ledger. Verification runs after selected discovery collectors, so advanced
references are included. Its bounded scope/omissions are explicit.

The legacy `collectors_connected` field is compatibility-only and can be true
only for complete selected coverage. Historical records without a valid ledger
show **not recorded**, even if their old Boolean was true. They remain readable;
this does not retroactively prove their source coverage.
Malformed ledgers are rejected against recorded mode/options, canonical scope,
selection, source outcomes and counts. Rejected raw coverage is removed from
API projections; the UI cannot grant completeness by reinterpreting it.
Collector corrections can legitimately change baseline comparison labels after
an upgrade. Review the changed evidence before accepting a new baseline or
allowlisting a finding; an upgrade-related difference is not a malware verdict.

Automatic referenced-file verification skips UNC/device paths, mapped remote
drives and unresolved relative commands without probing their targets. These
remain explicit unverified sources. It does not search an untrusted PATH to
resolve ambiguous commands. Explicitly chosen disk-scan roots are unchanged.
This is not a complete network-isolation or hostile-filesystem boundary: local
reparse-point redirection and drive-remapping races remain limitations.
PowerShell runs without execution-policy overrides. A blocked/unavailable module
is reported as incomplete evidence, not silently repaired or bypassed.

## Verification and Boundaries

Run `python tests/verify_project.py` with Node.js installed. CI uses Windows with
Python 3.11/3.13 and Node.js 22. It validates import/startup/configuration and
runs deterministic HTTP, concurrency, persistence and JavaScript regressions.
Tests use temporary fixtures, not private runner scans or system changes.
Unexpected skips and expected failures fail the strict runner.

See [the audit](v1.29-hardening-audit.md) for reproduced baseline findings and
[the verification record](v1.29-verification.md) for actual results, evidence and
unverified native/browser/Admin checks. Self-review is not an external audit.
The [manual browser-check procedure](v1.29-manual-browser-check.md) is for a
human operator; its existence does not mean those visual checks passed.
No merge or deployment is authorized as part of this stabilization branch.
